## 一、整体流程（建议顺序）

### 1. 测试准备与输入确认

- **拿到并锁定范围**：需求文档/PRD、设计稿（Figma）、接口文档、发布说明、已知限制。
- **确认测试类型**：功能、兼容性、性能、安全、无障碍、本地化、升级/迁移、合规（若有）。
- **定义入口与出口**：哪些版本算“可测”、什么条件下算“可发布”（见下文退出准则）。
- **搭建测试环境**：开发 / 预发 / 生产镜像（若允许）；账号角色（游客、普通用户、管理员等）；测试数据方案。

### 2. 制定测试计划（Test Plan）

写清：**目的、范围（测什么/不测什么）、假设与依赖、环境、角色分工、进度、风险**。不必长篇大论，但要可执行、可签字（或邮件确认）。

### 3. 需求可追溯矩阵 RTM（Requirements Traceability Matrix）

把**每条需求/用户故事**对应到**测试用例 ID**，保证“每条需求至少有一条用例覆盖”，避免漏测。

### 4. 设计测试用例（Test Case）

按模块写：**前置条件、步骤、预期结果、优先级（P0–P3）、测试数据**。手工测试的核心交付物。

### 5. 评审用例（可选但推荐）

产品/开发快速过一遍用例，修正歧义和边界。

### 6. 执行轮次

- **冒烟**：主干路径能否跑通（构建安装、登录、核心业务流程）。
- **系统测试**：全量用例执行。
- **回归**：缺陷修复后及每次合并重要改动后的受影响范围重测。
- **探索性测试**：不设脚本的有目的“捣乱”（弱网、快速点击、异常路径），补充脚本盲区。

### 7. 缺陷管理

统一工具（Jira、禅道、飞书项目等）：**重现步骤、环境、严重级别、附件（截图/录屏/日志）**。

### 8. 测试报告与退出

汇总：**通过率、未关闭缺陷、风险项、建议是否上线**。满足**退出准则**再推荐发布。

## 二、需要测试的内容（尽量全覆盖）

按层级拆开，你可根据项目勾选。

### A. 功能测试（最核心）

- **按业务域**：每个页面/每个用户任务（注册、登录、下单、支付、设置…）的**主路径 + 分支 + 异常**。
- **边界值**：空输入、最大长度、最小/最大值、临界日期、0 条数据、超大列表。
- **状态与数据**：列表为空/一条/很多条；加载中/成功/失败；草稿与已提交；权限不足时的行为。
- **业务规则**：计算公式、开关组合、互斥选项、依赖字段（A 选了才出现 B）。

### B. 界面与交互（UI/UX）

- 布局：不同分辨率、横竖屏、折叠屏/平板（若支持）、安全区（刘海、底部横条）。
- 控件：按钮可点区域、滑动、长按、焦点顺序（键盘/遥控器若适用）。
- 文案：错别字、截断、与设计一致性；错误提示是否可理解、可操作。

### C. 兼容性（Flutter 特别要看）

- **Android**：多版本（如官方最低 SDK 到最新若干版）、多厂商 ROM 抽样。
- **iOS**：多版本 iPhone/iPad 抽样。
- **Web**（若支持）：Chrome / Safari / Edge / Firefox 主流版本；不同窗口宽度。
- **屏幕密度**：小屏手机、大屏、平板（若支持）。

### D. 网络与环境

- Wi‑Fi / 4G / 5G；**弱网、断网、切换网络**（飞行模式开关）；请求超时、重试；离线缓存（若有）。
- **前后台切换**、杀进程再进、长时间后台恢复。
- **系统权限**：相机、相册、定位、通知等拒绝/仅本次允许/永久允许后的行为。

### E. 安装、升级与数据

- 首次安装、覆盖安装、从旧版本升级；**升级后数据是否保留**（登录态、本地配置）。
- 卸载重装；清除应用数据后的表现。
- App 体积、首次启动（冷启动）是否可接受（主观+简单计时）。

### F. 性能与稳定性（手工可做的）

- 列表滚动是否卡顿；大图/多图页面；长时间停留是否内存飙高（可配合系统开发者选项简单观察）。
- 高频操作是否 ANR/卡死；并发操作（快速连续点击）。

### G. 安全与隐私（基础专业项）

- 敏感信息是否在日志/截图中泄露；接口是否 HTTPS；本地存储敏感数据是否加密（若宣称）。
- 登录超时、Token 失效；越权访问（用低权限账号试高权限接口/页面）。

### H. 无障碍（若产品要求）

- 系统读屏；对比度；字体放大后的布局。

### I. 国际化与本地化（若有多语言）

- 语言切换即时生效；日期/货币/数字格式；长文案布局。

### J. 第三方与集成

- 登录（微信/Apple/Google 等）、支付、推送、统计 SDK：成功/失败/取消回调。
- Deep Link / Universal Link / App Links：从浏览器、短信、邮件打开指定页面。

### K. 与其他端一致性（若有）

- 与后端、管理后台、其他客户端**同一账号数据一致**。

### L. 发布与运维相关（若你们负责）

- 应用商店材料（截图、描述）与真实功能一致；隐私政策链接有效。

## 三、每条记录建议写什么（专业习惯）

### 1. 测试计划里

- 范围、不测项、环境、里程碑、风险与应对、角色。

### 2. 测试用例里（每条）

| 字段 | 说明 |
|------|------|
| 用例 ID | 唯一编号 |
| 模块 | 功能模块名 |
| 标题 | 一句话说明测什么 |
| 优先级 | P0 核心路径 / P1 重要 / P2 一般 / P3 边缘 |
| 前置条件 | 账号、数据、开关状态 |
| 步骤 | 按 1、2、3 可复现 |
| 预期结果 | 明确、可判定 |
| 测试数据 | 具体账号、订单号等 |

执行时在表格中加：**实际结果、状态（通过/失败/阻塞）、执行人、日期、构建号**。

### 3. 缺陷报告里（每条）

| 字段 | 说明 |
|------|------|
| 标题 | 现象 + 位置（简短） |
| 严重级别 | 崩溃/核心不可用/一般/文案/建议 |
| 环境 | 机型、系统版本、App 版本、网络 |
| 重现步骤 | 必写清 |
| 预期 vs 实际 | 对比写 |
| 附件 | 截图、录屏、日志（如有） |
| 频率 | 必现 / 偶现（注明尝试次数） |

### 4. 日报 / 周报（可选）

- 今日执行用例数、通过/失败、阻塞项、风险、明日计划。

### 5. 测试总结报告（轮次结束或发布前）

- **测试范围与版本**；**用例统计**（总数、执行、通过、失败）；**缺陷统计**（按级别、模块、趋势）；**未关闭缺陷与 workaround**；**残留风险**；**结论（建议上线 / 有条件上线 / 不建议）**。

## 四、退出准则（上线前建议约定）

示例（你们可改成条款）：

- P0、P1 缺陷全部关闭或有书面接受的变通方案。
- 核心场景用例 100% 执行且通过。
- 无未解决的崩溃级问题。
- 性能/安全项无“一票否决”项（按你们清单定义）。

## 五、给你的实操顺序（最小可行）

1. 要齐文档与设计 → 列模块清单 → 写 RTM。  
2. 先写 **P0 冒烟 + 主流程** 用例并执行。  
3. 再扩全量功能 + 兼容抽样 + 网络与权限。  
4. 修 bug 后做 **针对性回归** + 一次 **探索性测试**。  
5. 出测试总结报告，标明风险与是否建议发布。
