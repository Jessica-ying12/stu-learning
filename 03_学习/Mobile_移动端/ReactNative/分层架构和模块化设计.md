## 整体架构概览

整个应用从逻辑上可以分为以下四个核心层次：

1. **表示层 (UI Layer)**：负责界面的展示和用户交互。
2. **业务逻辑层 (Business Logic Layer)**：处理应用状态、业务规则。
3. **数据层 (Data Layer)**：管理数据获取（网络/本地）和数据持久化。
4. **导航层 (Navigation Layer)**：负责页面之间的路由管理。

此外，还有**工具层**和**类型定义层**作为支撑。

下面详细说明每一层包含的内容，以及在我们项目中的具体体现。

---

## 一、表示层 (UI Layer)

**职责**：渲染界面、接收用户输入、将用户操作转发给业务逻辑层。

### 包含内容：

- **`screens/`**：存放各个页面组件，它们是 UI 层的“大单元”，通常对应一个完整的视图。
  - `HomeScreen.tsx`：首页列表页
  - `DetailScreen.tsx`：详情页
  - `FavoriteScreen.tsx`：收藏页
  - `ProfileScreen.tsx`：个人中心页
  - `ScanScreen.tsx`：扫码页

- **`components/`**：存放可复用的 UI 组件（目前项目为了简洁未添加，但可扩展，例如自定义卡片、按钮、加载指示器等）。

**特点**：
- 页面组件内部**只负责 UI 呈现和交互事件绑定**，不直接处理数据获取或业务逻辑。
- 通过调用 **自定义 Hooks** 或直接使用 **Store** 中的状态和方法来触发业务逻辑。

**示例**：`HomeScreen` 中通过 `useEffect` 调用 `fetchMealsByFirstLetter`（来自数据层），并将结果存入本地 `useState`，但实际数据获取逻辑封装在服务中。

---

## 二、业务逻辑层 (Business Logic Layer)

**职责**：管理应用状态、实现业务规则（如收藏/取消收藏），作为 UI 和数据层之间的桥梁。

### 包含内容：

- **`store/`**：使用 Zustand 创建的全局状态管理。
  - `favoriteStore.ts`：管理收藏夹状态（`favorites` 数组）以及操作（`addFavorite`/`removeFavorite`），并集成持久化中间件。

- **`hooks/`**：自定义 Hook，用于封装可复用的业务逻辑（项目目前未单独创建，但可以按需扩展，例如 `useMeals` 封装获取菜品列表的逻辑）。

**特点**：
- 业务逻辑层**独立于 UI**，可以在不同组件中复用。
- Zustand Store 提供了全局状态，任何组件都可以通过 `useFavoriteStore` 获取和修改收藏状态。
- 持久化逻辑通过 `persist` 中间件在 Store 层处理，UI 层无感知。

**示例**：在 `DetailScreen` 中，点击收藏按钮时调用 `addFavorite` 或 `removeFavorite`，这些操作直接在 Store 中修改状态，并自动触发持久化存储。

---

## 三、数据层 (Data Layer)

**职责**：处理所有数据来源（网络 API、本地存储），并提供干净的数据访问接口。

### 包含内容：

- **`services/`**：封装所有网络请求。
  - `api.ts`：提供 `fetchMealsByFirstLetter` 和 `fetchMealById` 函数，负责与 TheMealDB API 通信，返回 Promise。

- **`utils/`**：工具函数（例如格式化日期、错误处理等），目前项目未用，但可按需添加。

- **`AsyncStorage`**（通过 Zustand 中间件集成）：用于本地持久化收藏数据，属于本地存储层。

**特点**：
- 数据层**隐藏了数据来源的细节**（是来自 REST API、GraphQL 还是本地缓存），上层只需要调用函数即可。
- API 函数返回的数据类型已经通过 TypeScript 定义，保证了类型安全。

**示例**：`HomeScreen` 中调用 `fetchMealsByFirstLetter('a')`，数据层负责发起 fetch 请求、解析 JSON、错误处理，最后返回 `Meal[]` 类型的数据。

---

## 四、导航层 (Navigation Layer)

**职责**：管理页面之间的跳转逻辑，定义导航结构。

### 包含内容：

- **`navigation/`**：存放导航配置。
  - `index.tsx`：配置底部标签导航（`BottomTabNavigator`）和堆栈导航（`StackNavigator`），并导出根导航组件。

**特点**：
- 导航层**集中管理路由**，使页面间的跳转关系一目了然。
- 通过 `@react-navigation` 库实现，支持传递参数（如 `Detail` 页面接收 `mealId`）。
- 导航配置与业务逻辑解耦，便于修改导航结构而不影响页面内部实现。

**示例**：点击 `HomeScreen` 中的卡片时，调用 `navigation.navigate('Detail', { mealId: item.idMeal })`，导航层根据配置找到对应的 `DetailScreen` 并传递参数。

---

## 五、支撑层

### 1. 类型定义层 (`types/`)

- **`index.ts`**：集中定义全局 TypeScript 类型（如 `Meal`、`FavoriteStore`、导航参数类型 `RootStackParamList`）。
- **作用**：确保跨层数据一致性，提供智能提示，减少运行时错误。

### 2. 工具层 (`utils/`)

- 存放通用工具函数，如日期格式化、字符串处理等。项目初始为空，但随着需求增加可以扩展。

---

## 数据流示例：收藏功能

为了更直观地理解各层如何协作，我们以“收藏一道菜”为例，梳理数据流动路径：

1. **用户操作**：在 `DetailScreen` 点击“加入收藏”按钮。
2. **表示层**：`DetailScreen` 中的 `onPress` 调用 `toggleFavorite` 函数，该函数内调用 `addFavorite(meal)`（来自业务逻辑层）。
3. **业务逻辑层**：`favoriteStore.ts` 中的 `addFavorite` 更新 Zustand 状态（`favorites` 数组新增一项），同时触发 `persist` 中间件。
4. **数据层**：`persist` 中间件自动将最新的 `favorites` 数组写入 AsyncStorage。
5. **UI 更新**：由于 Zustand 状态变化，任何使用了 `useFavoriteStore` 的组件（如 `FavoriteScreen`）都会自动重新渲染，展示新收藏的菜品。

**流程图**：
```
用户点击 → UI 组件 (DetailScreen) → Store Action (addFavorite) → 更新内存状态 → 触发持久化 (AsyncStorage) → UI 自动刷新
```

## 架构优势总结

这种分类划分方式带来了以下好处：

- **关注点分离**：UI、业务逻辑、数据访问各司其职，代码更清晰。
- **可测试性**：可以单独测试服务层、Store 逻辑，而不必依赖 UI。
- **可维护性**：修改数据源（例如换 API）只需改动 `services/`，不影响其他层。
- **可扩展性**：添加新功能时，只需在对应层增加代码，或创建新模块，不会引起全局改动。
- **团队协作**：不同开发者可以并行开发不同层，减少冲突。

---

## 总结

从架构角度，我们的项目分类如下：

| 分类                | 包含内容                                | 主要职责                         |
|---------------------|----------------------------------------|----------------------------------|
| **表示层**          | `screens/`, `components/`              | 界面展示与用户交互               |
| **业务逻辑层**      | `store/`, `hooks/`                     | 状态管理、业务规则               |
| **数据层**          | `services/`, `utils/`，AsyncStorage    | 网络请求、本地存储、数据处理     |
| **导航层**          | `navigation/`                          | 页面路由管理                     |
| **类型定义层**      | `types/`                               | 全局 TypeScript 类型             |

这种分层结构是高薪岗位面试中非常乐意看到的工程化实践，你可以在简历和面试中详细阐述你对架构的理解。希望这份解析对你有所帮助！
